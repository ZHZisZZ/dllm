Shared evaluation workflow

Fixed task definition

Select and record the pinned task variant, including its dataset split, prompt or chat template, few-shot context, stop sequences, answer filter, and scorer.

Recommended decoding

Use the configuration recommended by the official repository or paper, or the best-performing configuration reported there. Freeze it before test scoring and never select the best run after viewing test results.

Shared hardware

Run all evaluation and efficiency experiments reported here on NVIDIA H200 GPUs, with the accelerator count retained in the run record.

Native evaluation

Score one response per example unless the task declares repeats or multiple candidates, then apply the task’s extraction, normalization, and native evaluator.

The pinned lm-evaluation-harness submodule defines benchmark-side task configuration. Any model-specific prompt or few-shot variant is recorded with the result. View task configurations →

Shared scoring rules

Reasoning & QA

Exact match

Generated answers are extracted and normalized before comparison with the reference answer. Mathematical tasks may additionally use symbolic equivalence.

Multiple choice

Accuracy

The extracted option is compared with the gold label. Tasks may report raw accuracy or length-normalized accuracy as declared by the harness.

Code

pass@1

For the checked-in MBPP task, one generated program is executed against the supplied unit tests. The attempt passes only when all required tests pass.

Instruction & agents

Native success rate

IFEval uses its strict and loose instruction-following checks. Agentic tasks use their benchmark-provided verifier or final-state success rule.

Repeated runs and pass@k

Unless a task declares repeats or multiple candidates, one response is scored for each example. For repeated evaluations, every problem–repeat attempt is scored independently and the results are averaged over the benchmark. pass@k applies only to code tasks that sample multiple independent candidates and asks whether at least one of the k candidates passes. The current MBPP configuration reports pass@1; averaging repeated pass@1 results does not create a pass@k score.

TPF and throughput

Tokens per forward pass (TPF)

TPF measures how many realized output tokens a diffusion decoder advances per generation-time model evaluation. Across a benchmark, it is calculated as the total number of valid generated output tokens divided by the total number of denoiser forward evaluations (NFE), using summed counters rather than an average of per-example ratios.

  • Prompt tokens and padding are excluded from the numerator.
  • Early stopping uses the actual output length before EOS, not the maximum canvas length.
  • Rejected or re-noised positions do not count as output tokens, while the forward evaluations used to process them remain in NFE.

Output throughput (token/s)

Throughput runs use the model-specific SGLang serving implementation after warm-up. The reported calculation depends on the serving workload:

  • At concurrency 1, completion tokens are divided by the full request latency and the median is reported across repeated requests.
  • Under concurrent serving, all successful completion tokens are divided by the full benchmark wall-clock duration, with concurrency reported alongside the result.

DiffusionGemma and Nemotron Diffusion both provide model-specific SGLang serving paths for throughput measurement. Their upstream integration status differs, so every run records the exact implementation revision rather than relying only on an SGLang version label.

TPF measures decoding parallelism; token/s measures elapsed serving performance. They answer different questions and are never converted into one another.
